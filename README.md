# AI 招聘官

> **帮 HR 部门每天省出 3 小时：把筛简历、约面试、写面评这些重复性脑力劳动交给 AI，HR 只做最终录用决策。**
>
> *基准数据假设：HR 处理 1 份简历平均 3 分钟（初筛 1.5 分钟 + 邀约沟通 0.5 分钟 + 面评 1 分钟）× 日均 60 份 = 3 小时/天。AI 替代初筛与面评环节后，每天节省约 2.5-3 小时。*

## 为什么不用老办法（竞品差异化）

- **vs Moka / 北森（ATS）**：它们管流程，但**筛简历、面试、写评语这些脑力活还是要人一份份干**。本系统做脑力活自动化——规则+语义+证据链打分、AI 追问面试、面评自动生成。**与 ATS 并存而非替代**：ATS 管流程，我们管判断。**数据主从约定：Moka 是主数据源**——本系统只读入候选人信息（导出 API → Webhook 接收）、回写评估结果（备注字段 + 自定义标签），**不改变 Moka 原有状态机**；双向同步冲突时以 Moka 为准（对接在 M2 排期）
- **vs 直接把简历贴给 ChatGPT**：ChatGPT 是"临时工级"处理——HR 仍要逐份复制粘贴、无统一标尺、无存档、无法规模化。本系统提供**自动化规模化（1000 份批量）、一致化（同岗位统一标尺）、证据可追溯（评分卡留痕）**三大确定性

## 无感集成（核心价值）

```
候选人投递简历（钉钉审批流 / 招聘平台回调 / 本地上传）
  → POST /webhook/resume-uploaded 自动入库解析（授权日志留痕）
  → 自动初筛打分（规则60% + 语义匹配30% + 加分10%，评分卡留痕）
  → 自动 AI 面试（自适应追问 + 证据链评分）
  → 结果自动推送到钉钉 / 飞书 / 企业微信群里
  → HR 在群里看到「通过/驳回」建议，最终确认在群里 / 审批流中完成
  → Offer / 通知自动生成并推送
```

**HR 不用登录后台**——所有结果经群机器人送达，录用审批在群里完成。**审批法律效力说明**：群内"通过"按钮触发**钉钉审批流**（审批链路由企业自行配置，含电子留痕），本系统记录审批结论与时间戳（`approval_trail` 审批轨迹：业务审批 → 薪酬定薪 → 背景调查 → 最终审批，每环节留痕）；Offer 发送仅在最终审批通过后自动触发。接入方式见下文「外部系统接入」。

## 它靠谱吗

### 算法（可解释，不黑盒）

**综合分 = 规则层 60% + 语义匹配层 30% + 加分层 10%**：

1. **规则层（硬门槛 + 满足度评分）**：HR 配置的硬性条件（学历/年限/必备技能/薪资上限/排除词）由代码决策表判定，不满足直接淘汰**并输出原因**；全过时按满足度评分（技能命中率×60 + 学历富余×20 + 年限匹配×20）
2. **语义匹配层**：默认 TF-IDF + 余弦相似度（词表 100+ 技能词，无外部依赖可审计）；适配器接口，生产可换 Sentence-BERT / 腾讯云 TI
3. **加分层**：大厂背景 / 证书 / 项目复杂度关键词，人工规则加权（词表显式定义，增补即生效）

**评分卡**：每个候选人每次初筛生成一张卡（`score_cards` 表，保留最近 180 天自动清理）——硬门槛判定、三层得分、AI 证据链引用、人工复核留痕，全部摊开可查。**"A 为什么比 B 高 5 分"有逐层答案。**

面试与评估：自适应提问（动态难度由**代码正则判定**，非 LLM 自评）；多考官证据链评审（每个分数必须引用候选人原话）；加权总分由代码计算（LLM 只出维度分）。

### 数据库（企业级 schema）

SQLite 9 张表：候选人（状态机 + 授权日志 + tenant_id）/ 岗位规则 / 初筛 / 面试 / 批次 / 评分卡 / 通知 / Offer / HR 反馈。**多租户**：全表 tenant_id，查询按租户过滤（多部门/子公司数据隔离）。简历文件落盘 `resumes/`，解析文本入库，全流程从库调用。

**SQLite → PostgreSQL**：`DB_TYPE=postgres` + `DATABASE_URL` 环境变量切换（`db._conn` 双库分支已就位）。**不承诺无缝**，迁移清单（占位符/自增主键/ALTER/隔离级别/连接池）见「设计决策」章节。

### 容错设计（三个"怎么办"）

- **LLM 超时**：指数退避重试 3 次（1s/2s/4s），仍失败则该候选人标记失败、留在队列可重试
- **候选人中途断线**：面试状态落库（面试中），队列重试；断点续面在 M3 排期内
- **数据库写入失败**：操作级异常捕获，错误反馈到界面状态栏，已入库数据不受影响（SQLite 单文件事务）

### 合规（授权日志 + 偏见守护）

- 简历入库记录 `auth_source` 授权来源（候选人授权·本地上传 / 平台接口·授权）；生产授权动作：平台投递勾选条款 + 本地上传前页面勾选《候选人个人信息处理同意书》，候选人可要求删除
- **偏见守护测试**：打分与性别/年龄/姓名无关（确定性测试证明，`tests/test_algorithms.py::TestBiasGuard`）
- 候选人状态机全流程留痕：新入库 → 已解析 → 已初筛 → 初筛通过 → 面试中 → 待HR审核 → HR通过 → 已发通知 → 已发Offer → 已入职（含淘汰/驳回/申诉分支）

## 已知边界与设计决策

- **"智能匹配"的真实含义**：演示环境从内置简历库 / V2EX、Gitee 公开信息 / 本地上传匹配候选人，不对接招聘平台简历池；真实平台对接（BOSS/猎聘官方 API）为适配器占位，方案与工时见 `docs/02`
- **候选人 AI 模拟器**：自动面试演示由 AI 按简历人设扮演候选人，**未经过真人面试验证**；真人面试的延时/打断/偏离等问题是 M3 阶段（语音面试）的显式测试任务
- **词表为静态词表（更新机制明确）**：`algorithms.SKILL_LEXICON` 显式定义；更新机制 = **季度人工评审 + 热词建议入口**（HR 提交新词 → 待审核后生效），不在词表内的新词由语义匹配层替换位（Embedding 模型）兜底
- **PDF 解析质量**：中文 PDF 可能乱序/丢标点——解析失败不丢弃，入库标"待人工复核"（假阴性兜底）
- **API 用量为本地估算值**（按每次调用的实际消息长度动态估算 token × 刊例价，看板实时累计），精确计费需对接 DeepSeek 计费接口（M1=第 5-7 周）
- **数据删除为级联物理删除**：删除候选人时同时清除 5 张关联表记录（评分卡/面试/初筛/通知/Offer）+ 简历原文件，返回删除记录数（可审计）
- **语音面试的多口音 ASR 偏差**：文字层偏见守护测试已覆盖（性别/年龄/姓名无关）；语音层口音识别率差异是 M3 阶段的显式测试项。**测试方法（已定义）**：选取 5 种典型口音（东北/四川/广东/江浙/山东）各 30 个样本，对比 ASR 识别准确率与标准普通话基准，偏差 >10% 的口音标记为"需人工复核候选人"
- **申诉通道的重评逻辑（明确）**：申诉 ≠ 算法重跑（同算法同输入结果相同，无意义）。申诉 = **转人工复核**：被申诉候选人由 HR 手动评分，人工评分结果存入 `hr_feedback` 表，作为该岗位后续评估的校准样本（月度一致率报告纳入）——这才是闭环
- **入职后模块**（试用期绩效回传已上线：评级落库供月度一致率报告；培训系统对接在 M3=第 10-12 周）

## 设计决策（成本 / 并发 / 重试 / 双库）

- **成本（动态估算）**：看板「API 用量与成本」按每次调用的实际消息长度动态估算 token（× 刊例价）实时累计，非固定参考值。量级参考：初筛 1 人 ≈ 1 次调用（输入≈简历长度）；1 场 AI 面试 ≈ 15-25 次；1000 份初筛 ≈ 1000 次，粗估 ¥10-20（以平均简历 1-2k 字计，简历超长时按实际 token 累计）
- **1000 份简历**：演示同步执行（每批 20 份，看进度条）+ **异步后台任务**（已上线：提交即返回，完成自动推群）；生产异步任务队列在 M1（第 5-7 周）
- **并发**：Webhook 实时入库与批处理分离——Webhook 为独立 HTTP 服务同步写库（轻操作即时完成），批量任务在后台线程执行；SQLite 写锁等待 10 秒（`connect(timeout=10)`），生产高并发切 PostgreSQL
- **评分卡保留策略**：365 天（覆盖入职后试用期 3-6 个月绩效回传窗口，保证一致率报告数据完整）
- **真生产环境说明**（部署架构/监控告警/日志采集/SLA 承诺）见 `docs/04-系统技术架构图与迭代排期.md` 架构演进章节

## 上手（首次启动，需 Python 3.10+）

1. **配置 API Key**：在项目根目录建 `.env`，填入 `DEEPSEEK_API_KEY=sk-xxx`
2. **装依赖**：`python -m pip install -r requirements.txt`（约 1-2 分钟）
3. **启动**：双击 `start.bat`（自动装依赖 + 备份数据库 + 打开浏览器），或命令行在项目根目录执行：

```bash
python app.py        # 网页 http://localhost:7860，Webhook 端口 7861
```

4. **可选配置**（`.env`）：`ADMIN_USERNAME/ADMIN_PASSWORD`（登录鉴权）、`DINGTALK_WEBHOOK/FEISHU_WEBHOOK/WEWORK_WEBHOOK`（群机器人通知）、`WEBHOOK_API_KEY`（Webhook 鉴权）、`DB_TYPE=postgres`+`DATABASE_URL`（生产数据库）

演示数据：`demo_resumes/` 目录 10 份演示简历，可直接批量导入试跑全流程。

## 外部系统接入

**Webhook 入口**（端口 7861，随应用启动）：外部系统（钉钉/飞书审批流、招聘平台回调）POST 简历进来自动入库待初筛。`candidate_name` 为外部契约字段（内部映射到 `candidates.name`）：

```bash
curl -X POST http://127.0.0.1:7861/webhook/resume-uploaded \
  -H "Content-Type: application/json" \
  -d '{"candidate_name":"张三","resume_text":"简历全文...","source":"钉钉审批流","job_title":"AI 应用开发工程师"}'
```

**鉴权**：`.env` 配置 `WEBHOOK_API_KEY` 后请求必须带 `X-API-Key` 头；未配置时服务仅绑定 127.0.0.1（本机可访问）。

**群机器人通知**：面试完成/初筛完成事件自动推送到钉钉/飞书/企业微信群（`.env` 配 webhook 即生效，不配降级本地记录）。

**可配置数据源**：`ResumeDataSource` 抽象接口——本地文件夹为默认实现，BOSS/猎聘为 API 适配器占位。
